## 5-29 예외 안전성이 확보되는 그날 위해 싸우고 또 싸우자

-------------------------------------------------------------------------
- **예외 안전성의 조건**
  + 소프트웨어 시스템은 예외에 안전하거나, 예외에 뚫려있거나 둘 중 하나이다

```cpp
class PrettyMenu{
public:
  //배경 그림을 바꾸는 멤버 함수
  void changeBackground(std::istream& imgSrc);

private:
  Mutex mutex; // 이 객체를 유ㅣ한 뮤텍스
  Image *bgImage; // 현재 배경 그림
  int imageChanges;// 배경 그림이 바뀐 횟수 

};

void changeBackground(std::istream& imgSrc) {
  lock(&mutex); // 뮤텍스 획득
  delete bgImage; // 이전 그림 없앰 2
  ++imaageChanges;
  bgImage = new Image(imgSrc); // 새 배경으로 갱신
  unlock(&mutex); // 뮤텍스 해제  
}

```

위의 코드를 보면 이 클레스는 스레딩 환경에서 동작할 수 있도록 설계되어 병행성 제어를 위해 뮤텍스를 갖고 있는 코드이다.<br>
changeBackground 함수를 통해 예외 안전성에 대해 알아보자. <br>
예외 안전성의 조건은 다음과 같다. 

1. 자원이 새도록 만들지 않는다. → new Image(imgSrc)에서 예외를 던지면 unlock 함수가 실행되지 않기 때문에, 뮤텍스를 득했던 자원이 샌다.
2. 자료구자고 더럽혀지는 것을 허용하지 않는다. → new Image(imgSrc)에서 예외를 던지면, bgImage가 가리키는 객체는 이미 삭제되고, 새 그림이 깔린 것이 아닌데도, imageChanges 변수가 증가한다.

이 2가지 조건을 저 함수가 만조시키지 못하기 때문에, 예외 안전성을 만조핮 못하며 설계를 고쳐야 한다.

- **자원 누출 문제 해결**
  + Lock이라는 자원관리 객체를 만들어서 이 객체가 소멸될 때, unlock 함수로 해제시키면 자원 누출 문제는 해결된다.

```cpp
void PrettyMenu::changeBackground(stdd::istream& imgSrC) {

  Lock m1(&mutex); // 자원 관리 객체로 뮤텍스 획득, 이 객체가 소멸될 때 알아서 해제 됨.
  delete bgImage; // 이전 배경 그림 없앰
  ++imaageChanges; // 새 배경으로 바뀐 횟수 증가
  bgImage = new Image(imgSrc); // 새 배경으로 갱신

}
```

- **예외 안전성을 갖춘 함수가 제공하는 보장**
  + 예외 안전성을 갖춘 함수는 3 가지 보장 중 하나를 제공
  + 아무 보장도 제공하지 않으면 예외에 안전한 함수가 아니며, 현실적으로 대부분의 함수에 있어서 기본적인 보장과 강력한 보장 중 하나를 고르게 됨.


1. **기본적인 보장**
  + 함수 동작 중에 예외가 발생하면, 실행중인 프로그램에 관련된 모든 것들을 **유효한 상태**로 유지하겠다는 보장임.
  + 어떤 객체나 자료구조도 더럽혀지지 않으며, 모든 객체의 상태는 내부적으로 일관성을 유지하고 있음.
  + 하지만, 프로그램의 상태가 정확히 어떤지는 예상이 안될 수도 있음
  + 예를 들어 changeBackground 함수가 동작하다가 예외가 발생했을 때 PrettyMenu 객체는 바로 이전의 배경그림을 토대로 그대로 계속 그릴 수도 있고 아니면 기본 배경 그림을 사용할수도 있기 때문에 사용자는 예측할 수 없다.
    
2. **강력한 보장**
  + 프로그램의 상태를 **절대로** 변경하지 않겠다는 보장임.
  + 이런 함수를 호출하는 것을 **원자적인(Atomic)** 동작이라고 하며, 호출이 성공하면 마무리까지 완벽하게 성공함
  + 실패하면 호출이 없었던 것처럼 프로그램의 상태가 되돌아간다.
    
3. **예외 불가 보장**
   + **예외를 절대로 던지지 않겠다**는 보장임
   + 약속한 동작은 언제나 끝까지 완수하는 함수
   + 기본 제공 타입에 대한 모든 연산은 예외를 던지지 않게 되어 있는데, 예외에 안전한 코드를 만들기 위한 가장 기본적이며 핵심적인 요소임
   + 그러나 어떤 예외도 던지지 않게끔 예외 지정이 된 함수는 예외 불가 보장을 제공한다고 생각해서는 안됨.

- **자료구조 오염 문제 해결 전략**

기본적인 보장

```cpp

class PrettyMenu {
  std::tr1::shared_ptr<Image> bgImage;
};

void PrettyMenu::changeBackground(stdd::istream& imgSrC) {
  Lock m1(&mutex);
  bgImage.reset(new Image(imgSrc));
  ++imageChanges;
}

```

bgImage를 스마트 포인터에서 관리하게 되어 알아서 해제 시킴. <br>
배경 그림이 제대로 만들어졌을 때만, reset함수를 호출되기 때문에, 제대로 만들어지지 않는다면 delete도 호출되지 않음 <br> 
이러한 방법은 imgSrc의 생성자 호출 과정에서 에러 발생 시 문제가 일어나기 때문에 기본적인 보장임

강력한 보장

```cpp

struct {
  std::tr1::shared_ptr<Image> bgImage;
  int imageChanges;
};

class PrettyMenu {
private:
  Mutex mutex;
  std::tr1::shared_ptr<PMImpl> pImpl;
};

void PrettyMenu::changeBackground(stdd::istream& imgSrC) {
  using std::swap;
  Lock m1(&mutex);

  // 객체의 데이터 부분 복사
  std::tr1::shared_ptr<PMImpl> pNew(new PMImpl(*pImpl));
  // 사본 수정
  pNew->bgImage.reset(new Image(imgSrc));
  ++pNew->imageChanges;
  // 교체
  swap(pImpl, pNew)
}

```

복사 후 맞바꾸기(copy and swap)를 사용하여 새로운 객체의 사본을 만든 뒤 그걸 수정해서 바꿈 <br>
진짜 객체의 모든 데이터를 별도의 구현(implementation) 객체에 넣어두고 그 구현 객체를 가리키는 포인터를 진짜 객체가 물고 있게 함. <br>
즉, 연산에서 예외가 던져지더라도 원본 객체는 바뀌지 않고, 바꾸는 작업도 **예외를 던지지 않는**연산 내부에서 수행함 (std::swap)
이 전략은 객체의 상태를 **전부 바꾸거나, 아예 안 바꾸거나** 방식으로 유지하는데 아주 좋지만, 함수 전체가 강력한 예외 보장을 갖도록 보장해주지는 않음 

```cpp
void someFunc() {
  ...// 이 함수의 현재 상태에 대한 사본을 만들어 놓는다
  f1();
  f2();
  ...// 변경된 상태를 바꾸어 놓는다. 
}
```
만약 f1,f2가 예외 안전성이 강력하지 못한다면, someFunc함수도 강력하지 못함. <br>
f1, f2가 강력한 예외 안정성을 보장하더라도 상황은 나아지지 않음. <br>
f1이 끝까지 실행되면 f1에 의해 값이 변경되어 있을것이고, 만약에 변경된 값이 DB 값이면 사용자가 이미 확인해버렸을 수도 있기 때문에 돌이킬 수 없음. <br>
또한 효율도 무시할 수 없는데, 사본을 만들다 보니 복사 공간과 소모 시간을 감수해야 함 하지만, 안전성 측면에서는 강력한 보장이 좋음

C++ 레거시 코드는 예외 안전성 자체를 고려하지 않고 만들어진게 많기 때문에, 새로운 함수를 만들거나 기존의 코드를 리팩토링할 때, 어떻게 하면 예외에 안전한 코드를 만들까를 고민하는 버릇을 들어야 함.


- **5-29 정리**
  + 예외 안전성을 갖춘 함수는 실행 중에 예외가 발생하더라도, 자원을 누출시키지 않으며, 자료구조를 더럽힌채로 내버려 두지 않는다. 이러한 함수들이 제공할 수 있는 예외 안전성 보장은 기본적인 보장, 강력한 보장, 예외 금지 보장이 있다.
  + 강력한 예외 안전성 보장은 **복사 후 맞바꾸기** 방법을 써서 구현할 수 있지만, 모든 함수에 대해 강력한 보장이 실용적인것은 아니다.
  + 어떤 함수가 제공하는 예외 안전성 보장 강도는, 그함수가 내부적으로 호출하는 함수들이 제공하는 가장 약한 보장을 넘지 않는다.
